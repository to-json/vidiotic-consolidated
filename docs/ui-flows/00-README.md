# UI Flows

Textual traces of the user-facing workflows across the vidiotic family of apps,
reconstructed from code (not from running the apps). Each doc traces states,
transitions, key bindings, and on-screen affordances for one surface, and ends
with an honest "Observations" section calling out rough edges.

## How the surfaces relate

Two axes of workflow, which the individual docs don't fully connect:

- **In-app flows** — each app's own keyboard/mouse loop (docs 01–04).
- **Cross-app flow** — `vidiotic` is the engine; `vidiotic-ctl` and `vidiotic-prep`
  are sibling tools. They meet in two places, and both are **coherent by design**:
  - **`.vmap` control maps** (verified). `vidiotic-ctl` is the editor for *any*
    `.vmap`. It writes `global.vmap` (the player's bindings, layered under
    `vidiotic`'s embedded map) and `prep.vmap` (prep's editor keys, layered over
    prep's hardcoded defaults). The `Action` enum is two-namespace — flat player
    verbs plus `Action::Prep(PrepVerb)` — so one editor drives both apps and old
    files still parse. See ctl `store.rs`, `mapper.rs`, `model.rs`.
  - **The `.viproj` project + IPC** — `vidiotic-prep` exports HAP clips into a
    `.viproj`, and (if the running engine launched it) can hand that project
    straight back over the `vidiotic-wire` Unix socket. The socket is the same
    "anything the UI can do, a script can do" surface documented in
    `../ipc.md`.

For the *lived-use* read — where these flows are annoying or surprising to
actually operate, as opposed to whether they're internally coherent — see
[06-lived-use-friction.md](06-lived-use-friction.md).

## Cross-cutting review — do the flows make sense?

**Mostly yes, and they rhyme.** The four apps share a deliberate design language:
a vim-style mode word in the statusline (NORMAL / PLAY / EXPORT / ERROR / CMD),
layered control maps, learn-by-doing input capture, and the phosphor glyph
vocabulary. Someone who learns one app can read the others.

**Recurring gaps that show up in every surface** (these are design facts, not
doc errors):

1. **No undo anywhere.** vidiotic, prep, and ctl all apply edits immediately with
   no undo stack. Prep is the most exposed (destructive span edits, no recovery
   beyond autosave sidecars).
2. **No shortcut/help discovery.** The grammar which-key overlay is the *only*
   place bindings are surfaced; prep's 14 hardcoded keys and vidiotic's transport
   keys are invisible until you hover each button. No `?` / help mode.
3. **Learn mode has no cancel and no timeout** (ctl and prep). Click "learn",
   walk away, and it captures jitter indefinitely with no escape affordance.
4. **State that changes shape silently.** Camera cues grey out half the editor;
   prep's multi-source spans appear/disappear from the timeline depending on the
   open video; the "any device" (`device: ""`) binding looks identical to a
   concrete one. Each is defensible but under-signposted.

**Where the flows are genuinely strong:** the grammar state machine is small,
pure, and heavily unit-tested (root → conjugation → optional sticky, depth-2 by
construction); prep's frame-accurate seek-cache and non-blocking export worker
are solid; the layered-mapper design lets project-specific bindings coexist with
user defaults without shadowing.

**One correction applied during review:** doc 04 originally guessed prep's
large-file confirmation threshold at "~50 MB, no constant defined." The code has
`const LARGE_FILE_BYTES = 512 * 1024 * 1024` (512 MB, named) at `app.rs:33`.
Fixed in place. Everything else in the five docs was spot-checked against source
and holds up.

## Method / caveat

Generated by five parallel Haiku agents, one per surface, each reading only its
own files. Cross-surface claims and the correction above were verified against
source separately. These are code-derived reconstructions — they describe what
the code *does*, which is not always what a user *experiences*; anything marked
with a `?` in an individual doc is the agent flagging its own uncertainty.
